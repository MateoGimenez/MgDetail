# Backend: API, datos y avisos

**Carpeta:** `backend/`. Contrato completo de la API (con todos los campos y errores) en [backend/README.md](../backend/README.md). Este informe es el resumen.

## Qué hace

1. Recibe solicitudes de turno desde la landing (público, con protección anti-spam).
2. Autentica al dueño con una sesión por cookie.
3. Le permite gestionar las solicitudes desde el panel: listar, filtrar, cambiar el estado y borrar.

**Stack:** Node 24, TypeScript, Express 5 (librería para el servidor web), SQLite con el módulo nativo `node:sqlite` (no hay que compilar nada), zod (validación de datos), helmet (cabeceras de seguridad) y jose (sesiones firmadas, "JWT").

## API

| Método y ruta | Quién | Qué hace | Respuesta |
|---|---|---|---|
| `GET /api/health` | Público | Verifica que la base responda | `200 {"status":"ok"}` o `503` |
| `POST /api/bookings` | Público | Crea una solicitud de turno. Límite: 5 por IP cada 15 minutos | `201 {"booking": {...}}` (sin datos personales) |
| `POST /api/auth/login` | Público | Inicia sesión. Límite: 5 intentos fallidos por IP cada 15 minutos | `200` y cookie, o `401` |
| `POST /api/auth/logout` | Cualquiera | Cierra la sesión en el servidor y borra la cookie | Siempre `204` |
| `GET /api/auth/me` | Con sesión | Dice quién está logueado | `200 {"admin":{...}}` o `401` |
| `GET /api/admin/bookings` | Con sesión | Lista turnos, más nuevos primero. Filtros: `estado`, `limit` (1 a 100, por defecto 50), `offset` | `200 {"bookings":[...], "total": n}` |
| `PATCH /api/admin/bookings/:id` | Con sesión | Cambia el estado: `pendiente`, `confirmado`, `completado` o `cancelado` | `200 {"booking":{...}}` |
| `DELETE /api/admin/bookings/:id` | Con sesión | Borra un turno | `204` |
| `/api/admin/*` (cualquier otra) | Sin sesión | Responde `401` aunque la ruta no exista | `401` |
| `/api/*` desconocida | Cualquiera | Respuesta de error en JSON | `404` |

Los errores tienen siempre el mismo formato, con un mensaje en español listo para mostrar. Los errores de validación traen además `fields`, con el mensaje por campo.

## Datos que guarda

Base SQLite de un archivo (`DB_PATH`, por defecto `backend/storage/mgdetailing.db`). Dos tablas principales:

| Tabla | Contenido |
|---|---|
| `bookings` | Cada solicitud: nombre, teléfono, email, tipo de vehículo, modelo, servicio, fecha preferida, franja, comentario, estado, y fechas de alta y última modificación |
| `admins` | Email del dueño y hash de la contraseña (nunca la contraseña en texto) |
| `sessions` | Sesiones activas. Permite cerrar sesión de verdad y revocar todas al cambiar la contraseña |

El `id` que sale por la API es un UUID (un código aleatorio), no un número: un número secuencial revelaría cuántos turnos hay.

El teléfono se guarda tal como lo escribió el cliente. Para WhatsApp, la API devuelve además `telefonoWhatsapp`, calculado al leer, en formato internacional (por ejemplo `5493804123456`). Si no se puede interpretar, queda `null` y el turno igual se guarda.

## Seguridad incorporada

Según `backend/README.md` y el código (`backend/src/middleware/`, `backend/src/lib/`). La auditoría de seguridad terminó y corrigió algunos puntos (ver el [informe 05](2026-10-17_05_seguridad.md)): respuestas `404` para archivos inexistentes en `/assets`, `/fotos` y `/marca`; `X-Robots-Tag: noindex` en `/admin`; y permisos `0600` en la base SQLite (solo Linux). Los cambios de la auditoría no cambiaron el contrato de la API.

- **Contraseñas:** scrypt (algoritmo de hash que no es rápido de adivinar), con parámetros equivalentes a los que recomienda OWASP y sal aleatoria por usuario.
- **Sesiones:** token firmado, en cookie `HttpOnly` (el JavaScript de la página no la puede leer) y `SameSite=Strict`. Dura 8 horas. Cerrar sesión la revoca en la base.
- **Protección CSRF** (pedidos falsificados desde otra web): chequeo de `Origin` y de `Content-Type: application/json`.
- **Límites de pedidos (rate limit):** general por IP, 5 turnos cada 15 minutos, 5 logins fallidos cada 15 minutos.
- **Validación estricta:** los campos desconocidos se rechazan. Body máximo de 10 KB. Sin cuerpos comprimidos.
- **Base de datos:** todo parametrizado (sin armar SQL con texto). Una regla de ESLint lo exige.
- **Cabeceras:** helmet, CSP (política que limita de dónde puede cargar recursos la página), HSTS en producción, `X-Frame-Options: DENY`. La API responde `Cache-Control: no-store`.
- **Datos personales fuera de los logs:** el log solo guarda método, ruta, estado y tiempo. Al borrar un turno, el contenido se sobrescribe (`secure_delete`).
- **Honeypot:** un campo oculto que los bots completan. Si viene con contenido, la API responde como si hubiera guardado, pero no guarda nada.
- **Higiene de texto:** se quitan los caracteres de control bidireccionales (invisibles) que WhatsApp agrega al copiar un contacto. Los caracteres de control como el nulo se rechazan. Un test falla si algún archivo del código tiene caracteres invisibles escritos a mano.

## Avisos de turnos

Cuando entra un turno, el dueño puede recibir un aviso con el servicio, la fecha, el cliente, su teléfono, un link `wa.me` para escribirle y el link al panel (si está `PUBLIC_URL`). El aviso se manda **después** de guardar el turno y **sin esperar**: si el proveedor falla o tarda más de 5 segundos, el cliente igual recibe su confirmación.

**Estado actual:** desactivados. Por defecto `WHATSAPP_PROVIDER=none` (`backend/.env.example`). No pude confirmar el valor real de `backend/.env` porque no se lee por regla de seguridad.

**Privacidad:** con cualquier proveedor activo, el nombre, teléfono, vehículo y comentario del cliente salen del sistema hacia ese proveedor.

**Recomendación del resumen del orquestador:** Telegram para arrancar. El dueño todavía no eligió.

### Pasos para Telegram

1. En Telegram, buscar `@BotFather` (el oficial, con tilde azul), mandar `/newbot`, elegir un nombre y un usuario que termine en `bot`. Guardar el **token** que devuelve. Es una clave: no compartirla.
2. Abrir el bot nuevo y mandarle `/start` y un mensaje cualquiera. Sin esto el bot no puede escribir.
3. En el navegador abrir `https://api.telegram.org/bot<TOKEN>/getUpdates` (con el token). Buscar `"chat":{"id":...`: ese número es el **chat id**.
4. En `backend/.env` poner `WHATSAPP_PROVIDER=telegram`, `TELEGRAM_BOT_TOKEN=<token>` y `TELEGRAM_CHAT_ID=<chat id>`.
5. Reiniciar el servidor. Tiene que aparecer en el log `Avisos de turnos activados (telegram)`.

## Operación

### Desarrollo

`npm --prefix backend run dev` (o `npm run dev` desde la raíz, que levanta también el frontend). No hace falta `.env`.

### Producción

Un solo proceso Node que sirve la API y la web en el mismo dominio, detrás de HTTPS:

```
navegador --HTTPS--> Caddy o PaaS --HTTP--> node dist/index.js (API + web)
                                                |
                                                +--> SQLite (en un volumen persistente)
```

Pasos resumidos (detalle en `backend/README.md`):

1. `npm ci`, luego `npm run build` (compila frontend y backend). El build del frontend tiene que existir.
2. Variables mínimas: `NODE_ENV=production`, `JWT_SECRET` (32 caracteres o más, aleatorio), `FRONTEND_ORIGIN` (el dominio exacto con https), `SERVE_FRONTEND=true`, `DB_PATH` dentro de un volumen persistente, y la configuración del proxy:
   - **VPS con Caddy en la misma máquina:** `HOST=127.0.0.1` y `TRUST_PROXY=loopback`, con un firewall que cierre el puerto 4000 desde afuera.
   - **PaaS:** `HOST=0.0.0.0` y `TRUST_PROXY=1`.
   - `TRUST_PROXY=1` en un VPS con el puerto 4000 expuesto permite falsear la IP y saltear el límite de intentos de login (hallazgo S1 del [informe 05](2026-10-17_05_seguridad.md)).
3. Si falta algo obligatorio, el servidor **no arranca** y dice qué corregir.
4. Crear el administrador: `ADMIN_PASSWORD='...' npm run crear-admin -- --email <email>`.

**Lo que hay en el repo para desplegar:** no hay Dockerfile ni configuración de Caddy. Son recomendaciones del README, no archivos que se usen.

### Backup

No copiar el archivo `.db` mientras el servidor corre. Hacer una copia en caliente con `VACUUM INTO` (el comando de `sqlite3` o el equivalente con Node que está en `backend/README.md`), con `umask 077` para que la copia nazca solo legible por su dueño. La copia tiene datos personales y hashes: guardarla cifrada, con acceso restringido, y programarla con cron o el programador de tareas.

### Alta del administrador

Se hace por consola, no por la web. Si el email ya existe, cambia la contraseña y cierra sus sesiones. En desarrollo, `npm run crear-admin:dev -- --email <email>` (desde la raíz). En producción, `npm run crear-admin` (requiere `npm run build` antes).

## Límites conocidos

| Límite | Qué significa |
|---|---|
| Rate limit en memoria | Se reinicia al reiniciar el servidor y no se comparte entre instancias |
| Una sola instancia | SQLite no soporta varias réplicas escribiendo la misma base. Para este volumen alcanza |
| Consultas síncronas | Bloquean el proceso unos milisegundos por consulta. Con este volumen no se nota |
| WAL no funciona en red | No usar NFS ni SMB: la base necesita disco local o un volumen de bloque |
| Avisos sin reintentos | Cada proveedor se llama una sola vez. Si falla o tarda más de 5 s, el aviso se pierde (el turno sí se guarda) |
